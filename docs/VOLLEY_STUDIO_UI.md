# Volley Studio — проекты, анализ и просмотр розыгрышей

Локальный адрес: http://127.0.0.1:8875

Запуск Windows: `start-volley-ui.cmd`; PowerShell: `scripts/start-volley-rust-dev.ps1`
(единственный сервер — Rust; Python-эпоха осталась в защищённом чекпойнте).

## Последовательность работы

1. **Создать проект.** Название (по умолчанию дата) и выбор одного или нескольких видео из `project/`.
   Доступные файлы ищутся только при открытии окна создания/редактирования.
   Исходники остаются на месте. Одинаковые названия проектов запрещены.
2. **Анализ.** Один общий блок «Видео и диапазон анализа»: большое видео слева,
   добавленные записи проекта справа и шкала времени внизу внутри той же панели.
   Ниже расположен отдельный блок параметров запуска.
   Под горизонтальным разделителем располагается одна общая шкала на всю
   ширину панели: белый маркер перематывает видео, зелёные маркеры задают
   начало и конец анализа. Под шкалой остаются только два числовых поля
   границ начала и конца (в секундах) с автоматическим сохранением.
   Перетаскивание границ сразу обновляет значения полей, ввод секунд —
   перемещает зелёные маркеры. Воспроизведение и звук находятся
   непосредственно на видеоплеере; клавиши Пробел и стрелки управляют просмотром.
   Для каждой записи диапазон сохраняется отдельно.
   В панели запуска по умолчанию видны только пресеты для сравнения
   и кнопка запуска. Остальные параметры (VballNet/RAVEL, движок,
   разрешение кадра, CPU-потоки, классификация, трекинг и вложенные
   настройки моделей) находятся в закрытом разделе «Расширенные
   настройки анализа». Поля остаются частью той же формы: применение
   пресета изменяет их даже при закрытом разделе, а запуск анализа
   передаёт все выбранные значения. Подсказка на названии «Размер
   кадра анализа» показывается один раз: CSS-пояснение с дефолтом,
   без второго нативного title-пузыря.
   Доступны четыре проверяемых пресета: исходный контрольный,
   сбалансированный (рекомендуемый), агрессивное удержание ID и быстрый
   черновой. Выбор пресета показывает точные изменяемые параметры, а
   применение заполняет форму без запуска анализа, сохраняя выбранный
   движок и диапазон видео. Меняются пороги RAVEL/VballNet, длительность
   удержания ID, расстояние центров/IoU для связывания треков и параметры
   отслеживания мяча. Тест на первых 500 секундах сохранённых наблюдений:
   контрольный — 386 ID, сбалансированный — 261, агрессивный — 203.
   Это повторный запуск только алгоритма трекинга на тех же наблюдениях,
   не повторный инференс и не оценка точности распознавания человека.
   Агрессивное связывание может перепутать двух игроков. Порог отбора и минимум розыгрыша задаются в «Монтаже». Никаких обнаруженных событий,
   розыгрышей и статистики на этой вкладке нет.

   В нижней части вкладки есть отдельный «Ход обработки» с двумя полосами:
   общий прогресс всех видео и процент текущего этапа. Каждая запись
   проходит шесть реально подтверждённых стадий: нормализация, мяч,
   игроки, треки, события и подготовка результатов. Отображаются
   «выполнено X из N стадий», номер видео, счётчик кадров (если алгоритм
   его публикует), прошедшее время и журнал. Общая полоса не сбрасывается
   при смене видео/стадии и не показывает 100% до успешного завершения.
   Время каждой стадии и всего запуска записывается в
   `results/projects/<ID>/runs/analysis_timings/*.json`; под кнопкой
   запуска доступно время последнего анализа, включая после перезапуска UI.
   Старые запуски задним числом не хронометрируются.

   **Состав анализа задаётся в основной форме** (второго блока
   «Быстрый тест» нет): все этапы на всех видео проекта; все этапы
   только выбранного диапазона текущего видео; только RAVEL/игроки
   этого диапазона; только VballNet/мяч этого диапазона. Границы
   берутся из единственной шкалы исходного видео, а рядом с выбором
   показано фактическое начало, окончание и продолжительность.
   Применение пресета изменяет текущие параметры той же формы.
   Полный анализ проекта обновляет основной результат. Частичный
   запуск работает с отдельным каталогом эксперимента и НЕ заменяет
   файлы основного анализа проекта. Для одинаковых фрагментов
   подготовленная копия видео используется повторно, а каждый
   результат, параметры и время сохраняются под
   \`results/projects/<ID>/experiments/\` (при разном составе или
   порогах создаются разные ID). Имеющиеся результаты не удаляются.

   Вкладка «Результат анализа» восстановлена в исходном виде:
   одно видео, слои мяча и игроков, временная шкала, игровые
   события и список розыгрышей. Дополнительные выпадающие
   списки A/B и два видеоплеера удалены по запросу пользователя.
   Для выбранной вкладки маршрут \`?view=...\` применяется
   синхронно ещё в HTML до первого кадра браузера; начальной
   анимации перехода через «Анализ» при обновлении страницы нет.

   Для каждой записи диапазон сохраняется отдельно. Кнопка «Запустить анализ»
   обрабатывает все видео проекта последовательно. Предпросмотр исходного видео
   не зависит от наличия результатов анализа или ранее созданных копий.
3. **Результат анализа.** Единый блок, как на вкладке «Анализ»:
   слева видео с графической разметкой событий, справа прокручиваемый
   список исходных записей проекта. Выбор записи обновляет результат, не
   меняя проект. Даже если анализ записи пока не выполнен, она остаётся
   доступной в списке и отображается соответствующее сообщение.
   Под разделителем, внутри того же блока, находится временная шкала
   **на всю ширину блока**, не сжатая до ширины вертикального видео.
   На ней отображаются блоки розыгрышей, метки действий, текущая позиция;
   щелчок по свободной части шкалы перематывает видео.
   При событиях отображаются тип действия и track ID игрока, если
   определён, а также маркер мяча в координатах контакта.
   **Отдельная панель ниже** содержит список обнаруженных розыгрышей:
   щелчок запускает только выбранный интервал и останавливает воспроизведение
   в конце. Журнал выполнения анализа находится на вкладке «Анализ».
   В правом верхнем углу видео находится вертикальная панель флажков:
   **Все касания**, атаки, блоки, подачи, приёмы, верхние передачи и
   траектория мяча. «Все касания» — независимый белый слой для КАЖДОГО
   обнаруженного контакта, включая те, которые классификатор назвал
   атакой/блоком/подачей/приёмом/передачей, а не только `low_touch`.
   Семантические цвета: касание — белый, атака — коралловый, блок —
   фиолетовый, подача — бирюзовый, приём — жёлтый, верхняя передача —
   голубой, траектория — зелёный. Цвет одинаков на видео и шкале.
   Чекбоксы категорий независимы; «Все касания» можно отключить,
   сохранив цветные типы. Рядом показано число найденных событий
   **после фильтрации розыгрышей**, а для каждого события — confidence.
   Порог отображения 0/50/65/80% позволяет исключить низкоуверенные
   предсказания, но не улучшает качество самого классификатора.
   Настройки сохраняются в браузере отдельно для каждого проекта.
   Траектория отключена по умолчанию и загружается небольшими окнами
   из локального `ball.csv` через /api/analysis-trajectory.
   Линия показывает последние до 2 секунд движения, не соединяет
   длительные пропуски и обрезается по видеокадру с учётом zoom.
   Когда мяч не обнаружен в текущем участке, отображается зелёный индикатор
   состояния и кнопка «К мячу» для перехода к ближайшей сохранённой детекции.
   Никакие координаты не дорисовываются при их отсутствии. Для inline SVG
   состояние видимости меняется через removeAttribute/setAttribute("hidden"),
   а не через SVGElement.hidden: последний не всегда снимает фактическую
   CSS-скрытость. Повторный инференс не запускается.

   Названия технических параметров в настройках «Анализ», «Монтаж» и
   «Бенчмарк» подчёркнуты пунктиром и помечены ⓘ. При наведении курсора
   или фокусе с клавиатуры появляется подсказка с эффектом настройки и
   значением по умолчанию. Это именно значение при новом запуске, а не
   текущее пользовательское значение в форме. В блоке формирования
   розыгрышей на вкладке результатов подсказки работают аналогично.
   Словарь параметров находится в static/settings-tooltips.js.
   Под заголовком временной шкалы раскрывается раздел «Настройки формирования
   розыгрышей»: максимальный разрыв между игровыми треками (3 с), минимальная
   длительность эпизода (3 с), запас до/после (1,5 с). Настройки сохраняются
   локально в браузере отдельно для проекта; повторная детекция не требуется.
   Отображаются только траектории, которые track_calculator_with_court.py
   классифицировал как rally. Соседние игровые отрезки объединяются с заданным
   допуском и проверкой на technical_return. Это **кандидаты** в полные
   розыгрыши, а не достоверно восстановленные интервалы «подача — очко».
   Настройки этой шкалы не меняют исходные tracks или отдельные настройки
   вкладки «Монтаж». Для достоверного распознавания каждой подачи и конца
   розыгрыша необходимо дополнительно улучшать распознавание игровых событий.
   Координаты жёлтого маркера мяча используются в системе координат
   analysis_pixels и преобразуются в фактически отображаемую картинку с
   учётом CSS object-fit и масштаба zoom. Метки времени events/2 уже
   абсолютные и не требуют повторного прибавления analysis_offset_sec.
   Дополнительный чекбокс **«Рамки игроков · ID»** показывает цветные
   рамки RAVEL по сохранённому `players.json` и маленький Track ID в
   верхнем левом углу каждой рамки. По умолчанию выключен; окна детекций
   запрашиваются через локальный `/api/analysis-player-boxes`.
   Рамки совпадают с фактически отображаемой областью кадра, включая
   масштаб страницы. Track ID не означает постоянную личность.

   Раскрываемый блок **«Диагностика и экспорт по сохранённому анализу»**
   находится внизу вкладки результатов, а не среди параметров анализа.
   По отдельной кнопке штатные `track_processor.py` и `show_rally.py`
   создают диагностический MP4 с треками или отдельные клипы и PNG-снимок.
   Возможен экспорт `not_rally` для проверки ошибок. Файлы появляются
   ниже в виде ссылок; повторного инференса нет. Это диагностические
   материалы, а не полноценный монтаж розыгрышей.

4. **Игроки.** Для каждого видео доступна панель реальных игроков
   (по умолчанию пять слотов), поиск по ID/имени, длительность/уверенность
   каждого трека и фильтры: основные (10+ секунд), непривязанные,
   привязанные, короткие (<3 секунд), все. Программа показывает все
   наблюдаемые RAVEL track ID, даже если по ним не классифицированы игровые
   действия. Выбранные фотографии и возможные продолжения треков находятся
   рядом с панелью ручной привязки. Предложения формируются исключительно
   локально, по положению и времени рамок; одновременно видимые треки не
   предлагаются как один человек. Это не биометрическая идентификация и
   не автоматическое слияние: пользователь проверяет фотографии и вручную
   присваивает/снимает имя. Количество реальных игроков используется только
   как организационная настройка.
   На текущем часовом видео сохранены 2927 track ID, из них 2356
   длятся менее трёх секунд и 232 — 10+ секунд. Эти числа не означают,
   что записано столько разных людей.
5. **Отчёт.** Сводная статистика всех проанализированных записей.
6. **Бенчмарк.** Сравнение моделей VballNet и движков ONNX CPU, ONNX CUDA,
   OpenVINO CPU по методике исходного репозитория. История замеров по проекту.
7. **Монтаж.** Общий ролик из наиболее зрелищных полных розыгрышей проекта.
   Запуск остаётся на вкладке «Монтаж». Собственная панель показывает
   общий прогресс, текущую операцию, количество завершённых шагов,
   время и прокручиваемый журнал (как во вкладке анализа).
   Во время кодирования клипов используются фактические данные FFmpeg
   `frame/total_frames` — это процент кодирования текущего клипа.
   Сборка MP4 и опциональный экспорт Reels учитываются отдельно.
   Основной прогресс 100% означает успешное окончание всего монтажа,
   а не только последнего клипа. Время и шаги записываются в
   `results/projects/<ID>/highlights_manifest.json`.

   Границы игровых эпизодов в результатах и монтаже теперь определяются
   одним алгоритмом `scripts/rally_boundaries.py`. Он соединяет соседние
   `rally`-треки через кратковременные пропуски (по умолчанию до 3 секунд),
   не объединяет их через уверенный `technical_return` или новую подачу
   и ограничивает добавляемый контекст до соседних розыгрышей. При наличии
   надёжного `serve` используется его кадр; если такого события нет,
   начало остаётся первым сохранённым игровым треком. Окончание без
   достоверной разметки очка также остаётся эвристическим. Это не гарантирует
   восстановление реальной границы подачи/завершения каждого очка.

   `src/make_reels.py` получает единый JSON **на весь выбранный
   розыгрыш** (все составляющие треки + восстановленные границы) вместо
   отдельного файла на каждый фрагмент. Для вертикального видео включена
   двухмерная камера с адаптивным зумом: центр рассчитывается по X и Y мяча,
   приближение уменьшается при резком движении. Параметр
   `reels_zoom_max` по умолчанию 1,35 (1 — без зума, максимум 2);
   `reels_padding` задаёт дополнительный запас, ограниченный безопасным
   контекстом вокруг розыгрыша. Для горизонтальных исходников сохранён
   привычный сдвиг вертикальной области влево-вправо.
   Готовые вертикальные MP4 доступны в списке файлов вкладки «Монтаж»
   через локальный эндпоинт `/api/vertical-reels`; результаты остаются
   в `results/projects/<ID>/vertical_reels/`. Повторный анализ не нужен.

Границы розыгрышей и типы событий определяются алгоритмами приближённо.
Отсутствие события не означает, что его не было. Графическая разметка поверх
видео показывает **обнаруженные действия/контакты**. Рамки игроков с Track ID
можно дополнительно включить отдельным чекбоксом, используя сохранённые
покадровые обнаружения RAVEL.

## Форматы видео и быстрый просмотр

**Предварительно перекодировать видео не нужно.** Положите исходный файл
в `project/`, создайте проект и выберите запись. Видео можно смотреть без
запуска анализа и без восстановления файлов предыдущего проекта.

- Совместимый с браузером MP4/H.264 передаётся из оригинального файла.
- HEVC/H.265 и другие кодеки, читаемые FFmpeg, но несовместимые с браузером,
  просматриваются через небольшие H.264-фрагменты **по 18 секунд**.
  Запрашивается только нужное место; перемотка не обрабатывает весь матч.
  При непрерывном просмотре следующий фрагмент подгружается автоматически.
- Оригинал остаётся неизменным. В совместимый формат переводится только
  нужный участок, а **полного предварительного перекодирования нет**.
- Короткие временные клипы сохраняются в `results/ui_stream/` и переиспользуются
  между проектами; общий объём кэша ограничен **160 МБ**.

Исходный контейнер и кодек должны поддерживаться локальной сборкой FFmpeg.
Это не требование к ручной перекодировке: для большинства обычных записей
всё происходит автоматически при просмотре.

## Хранение

- `project/` — входные файлы.
- `results/projects/projects.json` — реестр проектов.
- `results/projects/<project-id>/project.json` — видео и диапазоны.
- `results/projects/<project-id>/analysis/` — новые вычисления.
- `results/projects/<project-id>/reports/` — отчёт.
- `results/projects/<project-id>/player_identities.json` — имена игроков.
- `results/projects/<project-id>/logs/` — журнал выполнения.
- `results/projects/<project-id>/benchmarks/` — замеры.
- `results/projects/<project-id>/highlights.mp4` — монтаж.

Старым проектам может быть закреплён исторический кэш общего анализа для чтения,
без копирования исходного видео. Новые данные генерируются отдельно по проектам.
Git исключает локальные видео, кэши, временные файлы и результаты.

## Разметка площадки до анализа

На вкладке **Анализ** выберите конкретное видео и подходящий кадр. Над видео нажмите **Разметить площадку**. На изображении последовательно поставьте восемь опорных точек:

1. Ближний левый угол площадки
2. Дальний левый угол
3. Дальний правый угол
4. Ближний правый угол
5. Условная середина боковой линии слева
6. Условная середина боковой линии справа
7. Левая точка сетки
8. Правая точка сетки

Для пляжного волейбола точки 5–6 не обозначают существующую разметочную линию атаки; это условные ориентиры. Готовые точки можно перетаскивать, последнюю — отменить, всю разметку — сбросить.

**Сохранить диапазон и разметку** записывает выбранные начало/конец и восемь состояний точек. Координаты сохраняются только для наблюдаемых или оценочных ориентиров. Ниже, в блоке **Настройки запуска анализа**, находится таблица по каждому видео: сохранённый временной отрезок и наличие разметки площадки. Разметка проекта хранится в `results/projects/<project-id>/courts/<filename>_court.json`.

При запуске анализа каждому видео явно передаётся **его проектный** `--court-json`. При отсутствии разметки передаётся `--no-court-fallback`: алгоритм не использует чужой файл или случайную глобальную разметку. Существующая разметка по умолчанию не копируется между проектами. Изменение разметки приводит к повторному вычислению стадий, которые зависят от геометрии, даже если распознавание мяча/игроков ранее было закэшировано.

**Ограничение:** один набор из восьми точек применяется ко всей выбранной записи. Для видео с движущейся камерой потребуется будущая покадровая/сегментная калибровка; текущий интерфейс не делает её автоматически. Не сохраняйте разметку другого ракурса.


## Универсальная разметка и отображение видео

Вкладка **Анализ** показывает исходное видео в его настоящей ориентации:
вертикальное видео остаётся вертикальным, горизонтальное — горизонтальным.
Плеер не растягивается до широкого прямоугольника с чёрными полосами.
Единая шкала времени имеет точно такую же ширину, как плеер.
Размытый фон при сборке Reels — отдельная монтажная функция, а не анализ.

Разметка площадки **необязательна**. По умолчанию редактор выключен;
анализ может запускаться и без неё. Геометрически зависимые события
в таком случае могут определяться хуже или не определяться.

Для разметки нажмите **«Разметить площадку»** над видео. Изображение
уменьшится, освободив место вокруг кадра. Далее просто щёлкайте по очереди
восемь точек. При щелчке внутри кадра сохраняются статус *visible* и
координаты кадра; за границей — статус *estimated* и реальные координаты,
возможно отрицательные. Предполагаемые точки показываются оранжевым.
Если положение неизвестно, нажмите **«Пропустить точку»**, чтобы записать
статус *unknown* и отсутствие координат. Можно отметить часть точек:
оставшиеся при сохранении будут обозначены как неизвестные.

«↶ Назад» отменяет последнее действие, «Сбросить» очищает черновик,
«Завершить разметку» выключает редактор. Ранее поставленные точки
можно передвигать; при повторном редактировании точки выбираются по порядку.
Кнопка **«Сохранить диапазон и разметку»** сохраняет и временной диапазон,
и статусы точек отдельно для каждого видео проекта.

При неизвестном угле матрица перспективы не создаётся, так как нельзя
использовать неизвестные координаты. Предполагаемый угол за кадром позволяет
строить перспективу, но она может быть неточной. Если камера движется,
одной статической разметки может быть недостаточно.

## Неподвижная строка и разметка на всей площади просмотра

Строка над плеером («Видео для анализа» · «Разметить площадку» · имя/размер/длительность)
имеет фиксированные размеры и расположение при включении/выключении разметки.
Дополнительные команды «Пропустить точку», «Назад» и «Сбросить» располагаются
поверх рабочей области и не перестраивают интерфейс.

Видеоплеер занимает **неизменную по размеру область левой колонки** независимо от
режима. Само исходное вертикальное видео остаётся вертикальным и центрируется
в поле; в режиме разметки его отображение уменьшается до 84% прежнего.
Вся свободная площадь вокруг изображения используется для установки
предполагаемых закадровых точек. Координаты вычисляются по фактическому
размеру изображения, а не по габаритам широкой колонки; точки за кадром
имеют статус estimated и могут получать отрицательные координаты.
Сервер валидирует расширенные координаты, но по-прежнему отвергает
экстремальные значения и неизвестные точки без надлежащего статуса.
Шкала времени и список записей не изменяют размеры при переключении.

## Автосохранение и быстрый сброс контекста

Под временной шкалой — два компактных числовых поля **без видимых подписей**
(для клавиатуры/скринридеров доступны названия начала и конца анализа).
Изменение значений и перемещение зелёных границ автоматически сохраняется
в проект через короткую задержку после редактирования, без кнопки
«Сохранить» и без текста «Сохранено» в обычном состоянии.
При ошибке показывается компактное сообщение рядом с полями.
Перед переключением видео или запуском анализа ожидается завершение записи,
чтобы не потерять последние изменения.

Разметка площадки сохраняется автоматически по мере постановки,
пропуска, отмены и перемещения точек. Автосохранение не закрывает
редактор и не сбрасывает историю. Данные сохраняются отдельно по видео
внутри проекта.

В блоке **«Сохранённый контекст по видео»** у каждой записи справа
есть кнопка **×**. Нажатие без подтверждения сбрасывает только эту

её площадки. Данные остальных записей проекта и исходное видео
не затрагиваются.

Шаги для отступов и размеров: 5 / 8 / 13 / 21 px (приближение
пропорций золотого сечения). Текст кнопки разметки и статус
расположены двумя симметричными строками по центру фиксированной кнопки.


## Разделение настроек анализа и монтажа

Во вкладке **«Анализ»** остаются только параметры вычислений:
движок обнаружения мяча (ONNX Runtime/OpenVINO), автоматическая/ручная
ширина кадра, CPU-потоки, тип площадки (пляжный волейбол).
Временной интервал и разметка сохраняются отдельно для каждого исходного
видео. Параметры монтажа не отправляются в задачу анализа.

Во вкладке **«Монтаж»** находятся:
- Желаемая длительность итогового ролика.
- **Минимум розыгрыша, с** — порог реальной продолжительности
  обнаруженного эпизода, без добавляемых монтажных полей.
- **Минимальная уверенность розыгрыша** — отбор только эпизодов,
  у которых эвристическая уверенность не ниже заданного значения;
  это **не порог нейросети обнаружения мяча**.

Анализ сохраняет широкий рейтинг кандидатов с низким предварительным
порогом, а монтаж фильтрует их без повторного запуска нейросетей.
Первичный расчёт треков допускает эпизоды от 0,5 секунды; отбор для
финального ролика происходит позже. Для проектов, рассчитанных старой
версией (которая сохраняла только заранее отфильтрованный ranking.json),
необходимо **один раз повторно запустить «Анализ»** для расширения рейтинга.
При наличии кэша нейросетевые предсказания переиспользуются; короткие
треки и рейтинг будут пересчитаны. Удалять существующие результаты не нужно.

В манифесте ролика results/projects/<project-id>/highlights_manifest.json
сохраняются применённые пороги монтажа, что позволяет видеть условия отбора.

## Ход анализа, рабочая шкала и использование CPU/GPU

После нажатия «Запустить анализ» интерфейс остаётся во вкладке
**«Анализ»** и прокручивается к блоку **«Ход обработки»**.
Там находятся журнал, текущий этап, кадры, скорость FPS и кнопка
остановки. Блок «Результат анализа» не показывает пустое видео,
пока обработка не закончена; в нём появляется информационная карточка.

Шкала содержит **один перетаскиваемый белый маркер** текущего положения.
Два значения времени расположены на кнопках **«Начало»** и **«Конец»**.
Нажатие соответствующей кнопки задаёт границу равной текущему
положению, синхронизирует выделенный диапазон и запускает
автосохранение. Отдельных перетаскиваемых границ или текстовых
полей секунд нет.

В списке движков явно различаются:
- **ONNX Runtime — CUDA (GPU)**: поиск мяча на видеокарте, CPU fallback
  для отдельных операций, недоступная CUDA вызывает ошибку.
- **ONNX Runtime — CPU**: поиск мяча только на CPU;
  число потоков устанавливается через SessionOptions.intra_op_num_threads.
- **OpenVINO — CPU**: альтернативный движок для мяча; игроки в любом
  случае определяются через OpenVINO CPU.

Здесь выбирается **число программных потоков CPU-инференса, а не число
физических ядер**. ONNX Runtime применяет `SessionOptions.intra_op_num_threads`,
OpenVINO — `INFERENCE_NUM_THREADS`; FFmpeg получает `-threads`.
Операционная система самостоятельно распределяет потоки по логическим CPU.
Volley Studio **не ограничивает CPU affinity** и не закрепляет ядра за задачей.
Например, 10 потоков на процессоре с 16 ядрами / 32 логическими CPU
не означает резервирование 10 ядер. Реальная степень параллелизма зависит
от модели и этапа обработки. При CUDA поле скрыто: CPU-этапы получают 8
потоков по умолчанию. Журнал выводит `CPU_THREADS_CONFIG` и настройки
детекторов. Документация: https://onnxruntime.ai/docs/performance/tune-performance/threading.html
и https://docs.openvino.ai/2026/openvino-workflow/running-inference/inference-devices-and-modes/cpu-device/performance-hint-and-thread-scheduling.html .

Нельзя перезапускать локальный сервер посреди активного анализа: задача
работает в дочернем процессе, а текущий сервер хранит ссылку на неё
в памяти. Обновлять статические HTML/JS/CSS безопасно; новые серверные
параметры применяются после штатного перезапуска между анализами.


## Контекстные CPU-потоки и прокрутка журнала

Поле **«Потоки CPU»** отображается в форме запуска анализа только
при выборе **«ONNX Runtime — CPU»** или **«OpenVINO — CPU»**.
Для **«ONNX Runtime — CUDA (GPU)»** оно скрыто и отключено, поэтому
не попадает в запрос запуска; сервер применяет стандартную настройку
для вспомогательных CPU-этапов. Введённое значение сохраняется при
переключении между движками без изменения уже запущенного анализа.

Журнал блока **«Ход обработки»** имеет ограниченную высоту и собственную
вертикальную полосу прокрутки. При нахождении внизу он автоматически
следует за новыми строками; если пользователь прокрутил вверх для чтения
истории, положение не сбрасывается при обновлении журнала.


## Локальный инференс без внешних нейросетей

Volley Studio не обращается к облачным ИИ-сервисам. Детектор мяча запускает
`src/inference_onnx_seq_gray_v2.py` или `src/inference_openvino_seq_gray_v2.py`
с локальными файлами `models/VballNet*.onnx` / `ov/VballNet*.xml`.
Игроков распознаёт `src/inference_player_ball_openvino.py` с файлами
`ov/RAVEL-VB-011-9f.xml` или `ov/RAVEL-VB-012-9f.xml` и соответствующими
локальными `.bin`. Трекинг, просмотр, монтаж, бенчмарк используют
локальные Python-скрипты репозитория, FFmpeg, OpenCV, ONNX Runtime и OpenVINO.

Браузер общается только с HTTP API на `127.0.0.1:8875`. Дополнительный
`src/celery_worker.py` поддерживает HTTP-загрузку *входных видео*, но
не запускается через Volley Studio. Это не внешний сервис нейросети.
Регрессионная проверка находится в
`tests/test_result_full_width_and_local_inference.py`.

## Расширенные настройки анализа и экспорта

На вкладке «Анализ» доступен раскрывающийся раздел параметров RAVEL-VB-011/012,
порогов игроков/головы/мяча, устройства OpenVINO, stride/frame-step,

На вкладке «Монтаж» отдельно настраиваются отступы вокруг розыгрышей

выбранные треки в results/projects/<project-id>/vertical_reels; параметры
smoothing, interpolation, margin, padding, smooth_window, smooth_polyorder
и fade-transition передаются реальному CLI. Основной горизонтальный
ролик сохраняется независимо от дополнительных вертикальных экспортов.

## Бенчмарк нейросетей по методике исходного репозитория

Для бенчмарка доступны только **VballNetV4c** и **VballNetFastV1**.
Каждый запуск всегда измеряет две модели последовательно: сначала VballNetV4c,
затем VballNetFastV1. Отдельный выбор модели убран и сервер не принимает
одномодельный режим. Результат появляется только после успешного завершения
обоих измерений. Режимы: ONNX Runtime CPU, ONNX Runtime CUDA (GPU),
OpenVINO CPU; CPU-потоки задаются только для CPU-движков.

Результат показан в виде двух карточек с полосами FPS, задержкой на один
вызов и отношением скоростей. Подробный журнал и история замеров свернуты.
Сравниваются только модели из одного запуска, чтобы не смешивать CUDA/CPU
и разные параметры тестов.

Методика повторяет scripts/bench_inference_fps.py исходного репозитория:
синтетический вход float32 штатного размера модели [1, seq, H, W];
по умолчанию **10 прогревов, 60 измерений и 3 независимых повторных загрузки модели**.
FPS одного повтора = число выходных кадров / медианная задержка одного вызова;
итоговый FPS — медиана трёх повторов.

Бенчмарк намеренно не читает видео, не вызывает FFmpeg, не распознаёт игроков
и не строит события. Это **чистый FPS модели**, который нельзя путать со
скоростью полного видеопайплайна. Результаты записываются в
results/projects/<project-id>/benchmarks/ с параметрами и задержкой в
миллисекундах. Архивные замеры старого FFmpeg-бенчмарка не удаляются,
но не отображаются как эквивалент нейросетевого теста.
