# Volleyball Reels Studio

Актуальное обновление: [Volleyball Reels Studio 2](volleyball-reels-studio-v2.md). Ниже сохранено описание первоначальной версии.

Локальный проектный Skill для Windows и WSL. Источники не удаляются и не изменяются. Серверы, API и подписки не нужны. Skill обнаруживается в `.agents/skills/volleyball-reels-studio/SKILL.md`; его нужно устанавливать вместе с репозиторием, кодом `scripts/volleyball_studio/` и моделями `models/`, `ov/`.

## Запуск

Поместите несколько видео и при необходимости музыку непосредственно в `project/`. Вложенные папки исключены, поскольку там могут лежать прежние результаты.

```powershell
powershell -ExecutionPolicy Bypass -File scripts/volleyball_studio/run.ps1
```

Команда задаёт пять вопросов: длительность, минимальный розыгрыш, количество роликов, эффекты, музыка. В чате используйте `$volleyball-reels-studio`.

```bash
cd /mnt/c/Users/amazomic/Desktop/github/fast-volleyball-tracking-inference
PYTHONPATH=scripts .venv/bin/python -m volleyball_studio --doctor
PYTHONPATH=scripts .venv/bin/python -m volleyball_studio --non-interactive --duration 30 --min-rally 4 --count 3 --effects cinematic --music yes --accents
```

Для новой установки: `uv sync`. Исходный проект требует Python >=3.14. FFmpeg и FFprobe должны быть в PATH (`sudo apt install ffmpeg` для Ubuntu). `uv sync` устанавливает CPU-пакет ONNX Runtime. Для CUDA выбирайте отдельное окружение с подходящим `onnxruntime-gpu` вместо `onnxruntime`, сверяя CUDA/cuDNN с текущей документацией. Не устанавливайте оба пакета в одно окружение. Приложение не меняет окружение автоматически. `--doctor` выполняет настоящий инференс; доступность провайдера сама по себе недостаточна.

Windows-обёртка использует `.venv/Scripts/python.exe`, если существует; иначе WSL `Ubuntu-25.04` и `.venv/bin/python`. При другом имени дистрибутива используйте прямую WSL-команду. Пути дополнительных параметров обёртки передавайте в синтаксисе выбранной среды, например `/mnt/c/...` для WSL.

Быстрая демонстрация на первых 25 секундах каждого файла:

```bash
PYTHONPATH=scripts .venv/bin/python -m volleyball_studio --non-interactive --analysis-seconds 25 --duration 8 --min-rally 2 --effects cinematic --music yes --accents --width 360 --output studio_demo
```

По умолчанию анализируется всё видео. `--analysis-start` и `--analysis-seconds` ограничивают тестовый участок; `--analysis-width 1280` задаёт разрешение прокси 30 fps. Рендер читает оригинал, переводит координаты прокси в исходное разрешение и экспортирует 1080×1920, 30 fps, H.264, AAC stereo 48 kHz, yuv420p, faststart. Можно выбрать ширину, кратную 18, например 360, 720 или 1080. Вертикальное поле зрения ограничено геометрией исходного изображения: все игроки не всегда помещаются.

## Исследование и повторное использование

Изучены README, PLAYER_CONTACTS, исходники детекции, геометрии, касаний, классификации и монтажа, а также три существующих локальных монтажных скрипта. Пользовательские изменения в них сохранены.

| Компонент | Как используется |
| --- | --- |
| inference_onnx_seq_gray_v2.py | VballNetV4c: основной ball.csv; CUDA с CPU fallback существующего загрузчика |
| inference_openvino_seq_gray_v2.py | Дополнительный путь `--backend openvino`, явно CPU |
| inference_player_ball_openvino.py | RAVEL-VB-012: игроки, track IDs и независимый мяч со score, CPU |
| track_calculator_with_court.py | Сегментация, устранение провалов, классификация, контакты |
| player_contacts.py | Через калькулятор с площадкой; без площадки тонкий адаптер переиспользует trajectory breaks и player reach без назначения сторон |
| court_coordinates.py / court_transformer.py | Существующая ручная разметка и преобразования площадки |

Модели уже находятся в репозитории: VballNetFastV1, V4c, GridV2b, GridV3, RAVEL-VB-011/012, их ONNX и OpenVINO IR. V4c выбран как основной по опубликованным в README метрикам точности; это не измерение точности на ваших матчах. RAVEL-012 выбран ради игроков и дополнительного мяча. TensorRT не включён и не объявляется проверенным.

Проверены доступные навыки `ffmpeg-skill`, `media-analysis`, Remotion и детерминированный video-editing-skill. FFmpeg отвечает за декодирование, аудио и экспорт; OpenCV за покадровую виртуальную камеру и координатные эффекты. Обёртки FFmpeg навыков не вызываются из runtime: у них нет готового контракта динамического спортивного монтажа с покадровой привязкой. Remotion не нужен для этой реализации; нейросетевые VFX и генеративная музыка не используются.

## Что определяет качество выбора

В `ranking.json` сохранены компоненты оценки:

`score = confidence × (events + duration + contacts + motion + exchanges + confidence_bonus)`.

Длительность даёт максимум 2 балла. События дают максимум 18: attack/block 3, dig/low_touch 1.5, overhead_pass 1, serve 0.8, с весом уверенности касания. Количество контактов ограничено 6 баллами; 85-й процентиль скорости в ширинах изображения за секунду даёт до 5; смены сторон до 8; уверенность до 5. Скорость в пикселях не является физической скоростью мяча в м/с. Статичный длинный трек без касаний отбрасывается. Technical return исключается.

Уверенность ограничивается эвристическим rally_confidence и покрытием уверенного мяча RAVEL. Порог по умолчанию 0.65. Это оценки моделей и эвристик, не калиброванные вероятности. Эпизоды выбираются по рейтингу без повторения пересекающихся участков между роликами. При необходимости последний эпизод сокращается вокруг сильного касания; `trimmed` фиксируется в manifest. Запрошенная длительность является верхней границей: при недостатке уверенных моментов получится более короткий ролик с предупреждением. При замедлении итог ограничивается этой же длительностью.

## Площадка и достоверность

Положите `<video_stem>_court.json` рядом с исходником, используя формат `court_coordinates.py` с размерами изображения и keypoints. Координаты автоматически масштабируются к прокси. Разметка должна соответствовать ориентации изображения после применения rotation metadata. Для пляжного волейбола добавьте `--beach`.

Автоматической модели площадки в репозитории нет. Без разметки касания, верхние передачи, приёмы и атаки остаются эвристическими; подача/блок и стороны команд не подтверждаются. Касания требуют изменения траектории и близости игрока, а не просто соседства с мячом. Даже с разметкой спортивная техника определяется эвристически: семантическая оценка безошибочности требует размеченного набора матчей и, возможно, дополнительной pose/action модели. Движущаяся камера и смены ракурса внутри записи требуют новой разметки или внешней модели геометрии. Без уверенных эпизодов программа завершается с ошибкой, не создавая случайную нарезку.

## Камера, VFX и звук

Камера использует траекторию и ближайшего уверенно найденного игрока, демпфирование и ограничение скорости панорамирования. После потери мяча более 0.5 с возвращается к центру. Эффекты модульные (`effect_state`, `apply_effects`): off, subtle, cinematic. Шлейф появляется на быстром уверенном мяче; вспышка при уверенном контакте; процедурное свечение с частицами и замедление 0.5× при сильной атаке только в cinematic. Это стилизованный огненный эффект, не фотореалистичная симуляция огня.

При широком горизонтальном ракурсе, если игроки выходят за пределы crop или уверенный мяч потерян, автоматически появляется обзорное окно из того же исходного кадра. Оно сохраняет контекст всей площадки; `--context-view off` отключает окно. Ложное обнаружение мяча всё ещё может смещать основной crop: обзорное окно уменьшает потерю контекста, но не исправляет точность модели.

Visibility CSV бинарен. Допуск эффектов основан на score RAVEL и проверке согласованности с основным детектором и соседним кадром. При потере уверенности шлейф обнуляется; эффекты выключаются. В `*.timeline.json` сохраняются координаты crop в пространстве прокси, исходный кадр, исходное время, повтор кадра при замедлении, координаты мяча и конкретные эффекты. У каждого эпизода есть локальная timeline; рядом с финальным MP4 находится объединённая timeline с глобальным output_frame и исходником каждого кадра, ограниченная фактической длиной экспорта.

Оригинальный звук сохраняется; при замедлении `atempo` следует той же карте кадров. Если звука нет, добавляется тишина. Музыка выбирается из найденных аудиофайлов (первый по имени) либо `--music-file`. Громкости: `--match-volume 1`, `--music-volume .15`, `--accent-volume .5`. `--accents` добавляет синтезированные короткие акценты к уверенным касаниям. Между эпизодами используется короткое затемнение изображения и звука; cinematic добавляет ускоряющийся zoom на границе эпизода, scale записывается в timeline. Лимитер ограничивает пики; измерение и двухпроходная нормализация LUFS пока не выполняются.

## Кэш и восстановление

`studio_work/<fingerprint>/` хранит прокси, CSV, predictions, tracks, ranking и журналы. Контентные хеши исходника, моделей, исходников CV и параметры инвалидируют соответствующие этапы. Готовые результаты проверяются по SHA256. Повторный обычный запуск создаёт новый каталог результатов, переиспользуя валидный кэш. Работа с несколькими видео последовательная: CUDA детектор и CPU детектор используют каждый свою среду, без переполнения VRAM и гонок декодеров.

```bash
PYTHONPATH=scripts .venv/bin/python -m volleyball_studio --non-interactive --duration 30 --min-rally 4 --count 3 --effects cinematic --music yes --accents --resume studio_output/КАТАЛОГ_ПРЕРВАННОГО_ЗАПУСКА
```

Параметры при восстановлении должны совпадать. Готовые этапы и сегменты не пересчитываются; незавершённый этап запускается заново. Возобновление с произвольного кадра длинного инференса пока не реализовано. Готовые MP4 без валидного маркера не перезаписываются. Файловая блокировка предотвращает одновременную запись нескольких процессов одной ОС в один work: запускайте последовательно либо с разными `--work`. Не запускайте одновременно Windows и WSL против одного каталога.

Показываются этапы 1–7, число видео/кандидатов/роликов, ошибки, elapsed и путь журнала. На рендере скорость и ETA вычисляются по обработанным кадрам. Пока подпроцесс прогревается, ETA неизвестна (`null`), полный tqdm доступен в журнале. Производительность измеряется реально и сохраняется в complete-маркерах, timeline и manifest, RAVEL отдельно сообщает model/pipeline FPS.

## Проверки

```bash
PYTHONPATH=scripts .venv/bin/python -m unittest discover -s tests -p 'test_volleyball_studio.py' -v
```

Проверяются целостность кэша, ограничение скорости камеры и границы crop, подавление эффектов при низкой уверенности/расхождении детекторов, отсутствие повторов эпизодов, предел длительности, отбрасывание длинной статики, исключение вложенных старых результатов. Каждая финальная MP4 проверяется FFprobe и полным декодированием FFmpeg `-xerror`. Результаты реального прогона записываются отдельно в `docs/volleyball-studio-validation.md`.

Официальные источники совместимости, проверенные при реализации: [ONNX Runtime CUDA](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html), [OpenVINO supported devices](https://github.com/openvinotoolkit/openvino/blob/master/docs/articles_en/about-openvino/release-notes-openvino/system-requirements.rst), [FFmpeg filters](https://ffmpeg.org/ffmpeg-filters.html). OpenVINO GPU относится к поддерживаемым Intel GPU; NVIDIA ускорение здесь обеспечивают ONNX Runtime CUDA и FFmpeg NVENC.
