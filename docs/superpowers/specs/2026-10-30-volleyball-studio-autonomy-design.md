# Автономный Volleyball Studio CLI

Дата: 2026-10-30
Статус: проект для согласования, реализация не начата.

## Цель

Стандартный запрос выполняется одним запуском локального CLI; агент получает компактный итоговый JSON. После первичной обработки создание 30-секундного Reels из атак с огненным мячом, музыкой и замедлениями не вызывает инференс, не требует чтения агентом треков и составления FFmpeg-команд.

## Подходы

1. Рекомендуется расширить существующий Python-конвейер. Сохранить анализаторы, композицию, VFX и QC; выделить интерфейс команд, индекс и зависимости стадий. Это позволяет использовать уже существующие алгоритмы и результаты.
2. Создать отдельный конвейер на Remotion. Потребует переноса координатных эффектов, аудио и QC и не даёт необходимого для этой задачи преимущества.
3. Добавить только оболочку над текущим main. Недостаточно: текущий повторный монтаж вызывает analyze, загружает CSV и все игровые треки, а ключ сегментов зависит от музыки.

Выбор подхода пользователем пока не подтверждён.

## Текущее состояние

- scripts/volleyball_studio/__main__.py объединяет весь цикл в одном main и уже имеет флаги analyze-only, resume, request.
- analysis.py имеет независимые маркеры normalize, ball, players, tracks, game_analysis с проверкой SHA256. Однако даже при попадании в кэш analyze повторно читает ball.csv, players.json и game-tracks.json.
- events.py сохраняет события без координатного массива; готового поискового индекса нет.
- select и composition.protect_timing уже автоматически выбирают интервалы и учитывают ретайминг.
- styles.py хранит пресеты в коде; dynamic/cinematic автоматически включают titles. Это противоречит текущей инструкции Skill о подписях только по запросу.
- render.py самостоятельно выполняет декодирование, VFX и кодирование, quality.py проверяет результат.
- Рабочее дерево содержит существующие изменённые и неотслеживаемые файлы. Их необходимо сохранить; автоматический commit всей рабочей копии недопустим.

## Контракт CLI

Использовать argparse без нового обязательного Python-фреймворка. Сохранить совместимость прежнего запуска через адаптер create. Windows launcher и python -m volleyball_studio должны предоставлять одинаковые команды.

| Команда | Поведение |
| --- | --- |
| create | Discovery, проверка кэша, недостающий анализ, индекс, план, рендер, QC |
| analyze | Анализ и индекс без монтажа |
| events | Ограниченная выборка из индекса по типу, confidence, Highlight Score, пригодности; сортировка и limit/offset |
| render | Только существующий проверенный анализ, план и монтаж; при отсутствии или устаревании кэша понятная ошибка без запуска нейросетей |
| status | Чтение короткого атомарного состояния запуска |
| inspect | Короткая диагностика, ошибки стадий и пути логов; полный лог только по явному запросу с ограничением размера |
| validate | Фактический QC указанного MP4 с сохранённой картой времени, без анализа исходных кадров |

Все команды: --help, --quiet, --verbose, --json; stdout по умолчанию содержит один компактный JSON. Прогресс в терминале идёт в stderr, подробности в файл. --quiet отключает прогресс. --verbose сохраняет машинный stdout. Ошибки argparse и рабочих стадий также имеют машинный контракт; коды выхода различают успех, неверные параметры, отсутствие достаточных событий, сбой и прерывание.

Итоговые поля: schema_version, command, status, videos_processed, events_found, outputs, report_path, log_path, errors, warnings. Коллекции ошибок ограничены; полный отчёт находится на диске. Парсинг результата не зависит от локализации текста ошибок.

## Индекс и загрузка данных

Локальный SQLite-индекс содержит source_id, event_id, rally_id, type, source_time_sec, analysis_frame, confidence, highlight_score, eligibility, ограничения классификации и ссылки на артефакты. Индекс строится после анализа и обновляется транзакционно. Координаты в индекс не копируются.

Отдельный компактный каталог кандидатов содержит интервалы, компоненты score, метаданные источника, контакты и ссылки на траектории. Фильтрация и выбор не читают покадровые массивы. Рендерер загружает только зависимости выбранных кандидатов. Для старого кэша предусмотрена явная миграция метаданных; нейросети при миграции не вызываются. Неполный или несовместимый старый кэш возвращает диагностику.

Без геометрии площадки не подтверждать подачи и блоки. Сохранять эвристический статус атак; отсутствие найденных атак не доказывает их отсутствие в матче. Не заполнять запрос другими событиями.

## План и пресеты

Пресеты classic, dynamic, cinematic хранятся в версионированных JSON. Включают реально используемые параметры VFX, переходов, аудио, ретайминга и кодирования; не оставлять декоративные настройки, которые рендер игнорирует.

editing/edit_plan.json создаётся программно до рендера. Содержит выбранные ID событий, интервалы исходника, порядок, целевую и достижимую длительность, карту ретайминга, параметры кадрирования, ссылки на данные, версии и ключи зависимостей. Рендер потребляет этот план. Карта фактически выведенных кадров сохраняется отдельно для QC.

Подписи выключены по умолчанию. Эффекты мяча включаются явным параметром либо явным запросом. Художественный стиль сам по себе не разрешает подписи. При отсутствии музыки или недостатке материала выдаётся короткое предупреждение без скрытой подмены.

## Согласование и повторное использование эффектов

Перед генерацией нового эффекта спросить пользователя, как он хочет, чтобы эффект выглядел. Уточнить существенные визуальные параметры: характер эффекта, цвет, интенсивность, длительность и движение. Можно предложить существующие варианты или попросить референс. Если эти пожелания уже указаны в запросе или ранее согласованы, повторно их не спрашивать. Дождаться ответа до генерации эффекта; независимые стадии анализа могут продолжаться.

После создания нового эффекта показать короткий предпросмотр и спросить, нужно ли сохранить его для повторного использования. Сохранение в библиотеку выполнять после явного согласия пользователя. Отсутствие ответа не означает согласие; артефакты текущего запуска сохраняются по обычным правилам.

При согласии сохранить эффект как воспроизводимый элемент локальной библиотеки: стабильный ID, название, версию, описание внешнего вида, параметры, необходимые ассеты, зависимости и предпросмотр. Сохранять реализацию и исходные ассеты, а не только готовый фрагмент видео. Координаты и тайминги конкретного матча передавать при применении, чтобы эффект можно было использовать с другими траекториями.

Перед созданием аналогичного эффекта проверять библиотеку и предлагать подходящий сохранённый вариант. При выборе существующего эффекта использовать его без повторной генерации. Если пользователь просит изменить внешний вид, уточнить только недостающие пожелания; изменённый вариант сохранять отдельной версией после согласия, не перезаписывая прежний.

Стандартный запуск с выбранным сохранённым эффектом сохраняет цель одного вызова CLI. Диалог о внешнем виде и сохранении требуется при создании нового эффекта. В монтажном плане и ключе кэша фиксировать ID, версию, параметры и хеши ассетов использованного эффекта.

Проверки: повторное применение сохранённого эффекта не вызывает генератор; отказ или отсутствие ответа не добавляет эффект в библиотеку; явно заданные пожелания не вызывают повторных вопросов; новая версия не меняет ранее сохранённый вариант.

## Кэш и восстановление

Ключи стадий разделяются:

- Нормализация: содержимое источника, диапазон, FPS, размеры, версия преобразования.
- Инференс: нормализованное видео, фактически выбранная модель и её SHA256, версия анализатора, параметры backend.
- События: инференс, геометрия, параметры и версия классификатора.
- Индекс: события, ranking, версия схемы индекса.
- План: индекс, фильтры, стиль, длительность, count и параметры ретайминга.
- Сегмент: исходник, выбранный интервал, траектория, камера, VFX, ретайминг, кодек. Музыка и громкость музыки не входят.
- Финальный звук и сборка: хеши сегментов, музыка, громкости, ducking, звуковые акценты.
- QC: итоговый MP4, карта кадров, версия и параметры проверок.

Сохранять SHA256 фактических артефактов, атомарные состояния и маркеры завершения. Прерванный этап не считается завершённым. Изменение музыки переиспользует сегменты; изменение VFX переиспользует анализ. render запрещает неявный инференс. Блокировка должна защищать общие записи кэша и индекс.

## Skill во время обычного запуска

Сократить основной SKILL.md до извлечения запроса, одного вызова CLI и проверки краткого результата. Ссылки на FFmpeg/Remotion/VFX нужны при разработке и нестандартном изменении реализации. Контракт references/events-editing-vfx.md обновить согласованно: убрать обязательное повторное чтение других skills при обычном запуске, сохранив требования к координатам и QC.

При разработке изучены текущие FFmpeg Skill, Remotion Best Practices и локальный VFX-контракт. Использовать существующие локальные модули; новый движок рендера для стандартного сценария не требуется.

## Проверки готовности

1. Все команды и --help; ошибки параметров и рабочих стадий возвращают валидный ограниченный JSON.
2. Индекс: фильтрация, сортировка, limit, повреждение и несовместимая схема; большие траектории не попадают в stdout.
3. Повторный render с запретом вызова анализаторов; изменение или повреждение источника/модели/артефакта обнаруживается.
4. Музыка меняет только сборку/звук/QC; VFX меняет сегменты, но сохраняет анализ; прерывание и resume не принимают частичный MP4 за готовый.
5. Автоматический план сохраняет выбранные атаки, учитывает замедления и сообщает недобор длительности.
6. Синтетический тест реального композитинга: известный мяч, attack, crop/zoom, замедление, короткий и длинный разрывы. Смещённый VFX и огонь до атаки должны проваливать проверку.
7. Интеграционный короткий MP4 с музыкой и VFX проходит реальный decode/QC; существующий анализ матча используется при наличии достаточных уверенных событий. Семантическая точность требует просмотра.
8. Отдельный воспроизводимый benchmark эффективности фиксирует число вызовов инструментов, байты stdout/stderr, чтения документации/JSON и число ручных решений по трассе. Различать измеренный CLI-тест и реальную агентную сессию. Сокращение токенов без измерений не заявлять.

## Решения, оставленные разработчику

Имена внутренних модулей, миграционный адаптер старого кэша и формат версионированного короткого отчёта. Не менять алгоритмы распознавания и не переустанавливать окружение без необходимости. Не добавлять комментарии в код, конфигурации или настройки. Не запускать полный повторный анализ матча ради проверки интерфейса.

## Уточнения после проверки проекта

- Планировщик вправе локально читать траектории только уже выбранных кандидатов, чтобы точно рассчитать ретайминг. Ограничение касается передачи данных LLM и загрузки всех треков до фильтрации. Для ускорения можно материализовать допустимые интервалы замедления в каталоге кандидатов.
- Первичная версия Highlight Score события использует существующий score его розыгрыша и явно сохраняет score_scope=rally. При равенстве сортировать по confidence, затем source_time_sec и event_id. Не выдавать эту оценку за отдельную обученную модель контактов.
- status и inspect требуют --run; validate требует --run либо MP4 вместе с --timeline. render принимает --work и необязательный --plan. При отсутствии плана создаёт новый план из индекса. Последний запуск не выбирается неявно.
- Итоговый stdout ограничен 8192 байтами, списки ошибок и предупреждений — пятью элементами каждый; events по умолчанию limit=10, максимум 100 с сохранением полной выборки в файл при превышении лимита stdout. Прогресс в stderr обновляется не чаще раза в 10 секунд и при смене стадии. --verbose пишет подробности в лог, итог остаётся ограниченным.
- Benchmark сравнивает старый и новый пути на одном fixture и одинаковом запросе. Сохраняет число действий, байты инструментальных ответов, повторные чтения и ручные решения. Для новой трассы цель — один запуск и максимум одно чтение краткого отчёта; stdout не более 8192 байт, отсутствие выдачи CSV/траекторий и чтения вспомогательных skills. CLI-тест не обозначается как измерение токенов живой агентной сессии. Если прежняя трасса недоступна, baseline отмечается unavailable и процент сокращения не вычисляется.
