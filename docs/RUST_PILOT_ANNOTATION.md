# Пилотная независимая оценка

Статус: подготовка к разметке. Человеческих меток и измерений качества пока нет.

## Кандидат для разметки

- Источник: `examples/gtu_20250316_002.mp4`, 33,066367 с, 1920×1080, 991 кадр, H.264.
- Частота кадров: 30000/1001 FPS. Не округлять её до 30 при переводе кадров во время.
- SHA-256: `d92c2e1b3014efd51c62e917488366d8804b225ed4aaad77c025d5af914f7a80`.
- Предлагаемый диапазон: весь файл, 0–33,066367 с. На обзорных кадрах видна волейбольная площадка; пригодность для точной разметки касаний и полных границ розыгрышей должна быть проверена человеком при покадровом просмотре.
- Перед разметкой проверить SHA исходного файла. Исходник не перезаписывать, предсказания модели разметчику не показывать.

## Протокол разметки

1. Независимый человек просматривает оригинал, отмечает полный диапазон, пригодный для оценки, и фиксирует видимые границы каждого розыгрыша. Обрезанные границей файла или неясные эпизоды отдельно помечаются и исключаются из выбранного оценочного диапазона; отсутствие события не следует угадывать.
2. Внутри выбранного диапазона отмечаются все видимые касания: время контакта в секундах от начала исходного файла и, только когда игрок достоверно различим, устойчивый анонимный `player_id`. Сомнительные контакты требуют отдельного решения разметчика до расчёта.
3. Для оценки трекинга заранее выбрать равномерные кадры, например каждый 30-й, а также кадры перекрытий. На каждом выбранном кадре разметить рамки всех видимых игроков и сохранить единый анонимный `person_id` для одного человека. Записать нулевой номер кадра и нормированные `[x, y, width, height]` относительно 1920×1080. Имена спортсменов не требуются. Кадры без размеченных людей текущий оценщик не учитывает.
4. Зафиксировать имя или псевдоним разметчика, диапазон, частоту, метод и SHA-256 разметки. Не называть машинные предложения независимой разметкой; желательно, чтобы спорные метки проверил второй человек.
5. Только после фиксации меток получить результаты Rust для того же исходника и диапазона в изолированном проекте. Для сравнения с Python нужны сопоставимые результаты на том же источнике; их наличие пока не подтверждено. Не заменять фактические идентификаторы игроков идентификаторами треков без проверенного соответствия.

## Формат для существующего оценщика

В `scripts/ci/test_rust_parity_84.mjs` приведён синтетический пример схемы `volley-parity-evidence/1`. Для настоящего прогона в `truth` указываются `kind: "human_independent"`, `annotator`, массивы `touches`, `rallies`, `tracks` и `annotations_sha256`. SHA рассчитывается по UTF-8 байтам `JSON.stringify({touches, rallies, tracks})` в указанном порядке. Времена в секундах относятся к исходному файлу, рамки — к оригинальному кадру. Оценщик ограничивает номера кадров длиной диапазона, поэтому для диапазона с ненулевым началом следует использовать индексы от начала диапазона, одинаковые в метках и предсказаниях, и документировать соответствие кадрам оригинала. Точный `fps` должен совпадать во всех разделах; использовать численное значение `30000/1001`.

Тот же формат массивов требуется для предсказаний, вместе с их SHA и идентичными SHA источника, весов и настроек. Оценщик рассчитывает Touch F1 при допуске ±0,15 с, Rally F1 при IoU ≥ 0,5 и IDF1 на размеченных кадрах при IoU рамок ≥ 0,5. Эта короткая выборка пригодна для поиска конкретных ошибок, но не для вывода о качестве на полном матче.

Строгий оценщик этапа 84 дополнительно требует сравнимые Python и Rust, показатели производительности и внешние проверки CUDA и Docker. Его итог NO-GO при отсутствии этих данных не означает, что метрики отдельного Rust-прогона можно считать готовыми. Инструкции полной приёмки: `docs/RUST_BENCHMARK_84.md`.
